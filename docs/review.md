# 评审与实施顺序

本轮交付是方案和品牌设计资产。以下阶段在文档确认后开始；当前没有创建应用、agent runtime 或产品能力包。

## 1. 已明确的原则与待验证方案

用户已明确：核心保持最精简，能通过标准可插拔机制实现的功能都放在核心外。功能重要不代表必须打包进 App。完整 pi 能力、原生自定义界面、AFM 默认模型和英文首版继续保留。

| 决策 | 当前方案 | 影响 |
| --- | --- | --- |
| Runtime | 完整 pi SDK + 薄 TS sidecar | 复用资源、扩展、工具、会话；随应用打包 Node |
| 默认模型 | AFM 纯推理，由 pi 执行工具 | 验证上下文、动态 schema、流式与取消 |
| 领域能力 | owner 维护的 skill / scripts / extension / MCP | 可独立安装和升级，不进入 App 构建依赖 |
| macOS 能力 | 首版无内置 Swift capability service | 权限、依赖与执行方式属于实际能力包 |
| 扩展 UI | 通用原生语义控件 + 同会话 TUI 兼容视图 | 属于宿主适配，保留公开扩展机制 |
| 资源与认证 | 沿用 pi 原格式与机制；独立 agentDir | 不增加新 skill 格式或认证存储层 |
| 视觉 | 自定义聊天界面；Phosphor；Nano Light/Dark | 保留键盘、文本输入和可访问性 |
| 语言 | 首版英文，文案可后续本地化 | 不实现其他 locale |
| 品牌 | Sine 标志；Nano Light 紫色、Nano Dark 蓝色两套配色 | 数学代码生成；透明与实底、字标、app icon、favicon 和辅助物料 |
| 分发 | Developer ID、公证、站外分发 | 验证核心运行时；可选 helper 独立分发 |

本轮移出首版方案：内置系统工具服务、私有工具 CLI、App 级桌面协调器、预装领域能力包、独立权限中心和独立 Keychain adapter。

## 2. 阶段一：验证核心成立的条件

| 验证 | 问题 | 通过条件 |
| --- | --- | --- |
| AFM provider | 不注册 executable Tools 能否产生 pi 工具调用？ | 文本、schema、流式、验证、取消、连续调用成立 |
| 上下文预算 | 真实 skills / tools 能否有效使用？ | 按需加载、发现和超限处理有实际验证 |
| Extension UI | SDK 能否挂接完整公开 UI 接口？ | mode guard、组件、editor、renderer、theme、生命周期可用 |
| Runtime packaging | Node、pi、AFM 能否稳定随 App 运行？ | 签名包、干净机器、离线核心任务、资源加载验证 |

这一步不开发通用 macOS 工具服务。验证结果如需调整模型策略或 pi 兼容范围，应明确评审，不能静默换云模型或删功能。

## 3. 阶段二：最小运行宿主

建立必要 IPC、SDK 生命周期、资源发现、pi 会话持久化、AFM bridge、取消和恢复。直接保留 pi 的工具与认证语义，原生索引仅用于聊天展示。

通过条件：普通对话与工具调用闭环；skill / package 发现；steering / follow-up；fork / resume / compaction；MCP / codemode / tool-search 的显式接入；退出与异常恢复。

## 4. 阶段三：界面与完整扩展兼容

实现设计文档中的通用组件、聊天、资源入口和必要的命令适配。每个聊天的扩展与界面共用该聊天的真实 pi session；任意 TUI 组件通过兼容视图承载，不为每个插件开发专属原生页面。

通过条件：公开 UI 接口有真实实现；键盘与 accessibility 可用；英文文案完整；深浅主题可读；应用操作图标全部来自 Phosphor。

## 5. 阶段四：可插拔验证与发布

用已有或独立开发的能力包验证宿主：一个只有 skill + shell 的简单包，一个带 extension 或 MCP 的结构化工具包，以及需要外部 helper 的包。它们使用标准安装和资源发现机制，不变成核心依赖。

通过条件：安装、移除、重载和独立升级成立；未安装领域包时 App 正常运行；包内脚本和相对资源可使用；工具失败与扩展交互可呈现；签名版本核心运行稳定。

产品能力通过真实任务评估，记录完成率、错误类型、调用与耗时。执行方的领域权限和并发语义按包本身验证。测试不连接真实数据库；本轮只检查文档和品牌资产，不运行 HURL、OrbStack 或应用构建。

## 6. 迭代判断

新增需求先尝试 skill、脚本、pi extension 或 MCP。只有现有宿主无法承载通用能力时，才考虑核心改动；修改核心的目标是补齐通用宿主机制，不搬入某个工具的领域实现。

本轮文件保持在独立 SSD 工作树。架构和品牌方向仍等待评审，应用尚未开始实现。
